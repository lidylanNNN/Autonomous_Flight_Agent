# 机器人 Agent 项目面试复盘

整理日期：2026-11-18。目标岗位是机器人 Agent 开发，重点准备系统集成、工具调用、状态管理、排错和评测证据方面的追问。

本文是面试准备材料。实现和验收事实以各案例链接的阶段记录、契约及原始证据为准；本文不重新定义项目进度。后续开发出现有面试价值的问题时，按同一格式追加，并更新原案例的解决状态。

## 使用方式

- 每个案例先讲具体失败，再讲如何缩小范围、如何处理及如何确认有效；不要只列技术名词。
- 面试时按实际经历说明本人承担的需求、设计、审查、联调或分析工作，以及 Coding Agent 的协助范围。项目代码或测试通过，不自动证明本人掌握了相关能力。
- 运行输入由脚本写入真实终端，不能说成人工现场操作。SITL 是 PX4/Gazebo 仿真，不能说成真机部署或商业交付。
- “固定输入下通过”“故障注入验证”“测试替身覆盖”和“生产问题已修复”分别表述；未知根因不补造解释。

## Q01：拍照和检测已成功，为什么整轮还超时？

**场景与现象**：M6 T04c 的地面任务要求拍照、检测并等待。两次运行都已完成拍照和检测，整个验证却迟迟无法结束。

**定位与原因**：检查原始模型回复及线程记录，发现模型额外生成了末尾 `hold`。当时未启动飞行动作服务，执行器卡在该服务的发现等待；不是检测结果没有返回。

**实际处理**：保留两次失败记录，在后续运行前明确固定输入为“只执行拍照与检测两个动作、禁止悬停”。没有修改模型原文、系统 prompt 或执行器来把失败计成成功。

**验证与边界**：后续真实地面链路通过，模型只生成两个动作，检测收到本轮拍照的原始输出。这只证明明确输入下可用，没有证明任意自然语言都不会多加动作，也未新增规划语义校验。

**可能追问**：如何区分服务发现超时和响应超时？动作白名单为什么没拦住 Hold？

**回答重点**：Hold 是允许的动作，白名单不能判断它是否符合本轮任务。排错要把模型实际计划、已执行步骤和正在等待的服务对应起来。任务语义检查与工具合法性检查负责不同问题。

依据：[M6 T04c 失败记录](../plans/M6.md#t04c-agent-拍照后检测2026-11-18)。

## Q02：模型生成了合法起飞参数，为什么仍然拒绝起飞？

**场景与现象**：M5 4b-1 首轮，模型正确生成起飞到 3 米的请求，Gate 返回 `STALE_STATE`，飞机没有解锁。

**定位与原因**：核对 Gate 原因、状态时间及后端记录，问题出在决策使用的状态已过期。聚合状态的年龄受最旧的必需 Topic 接收时间影响；收到近期位置，不代表全部必需状态都足够新。

**实际处理**：保留该失败，未放宽安全新鲜度要求。后续独立场景完成两轮起降，但没有把复跑通过记录为时序问题已经修复。

**验证与边界**：失败轮后端零执行，成功轮有实际命令、ACK 和最终落地状态。当前能确认拒绝保护起作用，不能确认状态时序风险已消除。

**2026-11-18 新证据**：M6 T05b 两次运行再次被拒绝：一轮起飞成功后，P1 GoTo 返回 `STALE_STATE`，后续视觉动作和 RTL 均未执行，停止仿真前仍在空中；另一轮 Takeoff 返回 `STALE_STATE`、`SYSTEM_UNHEALTHY`，零飞行动作派发。安全拒绝停止了后续派发，但不等于已经完成空中安全处置。该轮运行结束时尚未定位状态为何过期，未把仿真退出说成正常落地。

**后续排查**：冻结 PX4 在着陆状态不变时约每秒发布一次该消息，变更前统一 1000 毫秒时效窗口没有给缓存和审查留下充分余量。一轮快照年龄为 965 毫秒，到决策记录时已为 1043 毫秒；另一轮快照中仅着陆消息过期，联带判为链路不健康。归档状态和生产 Supervisor 的离线回放复现了这两类拒绝，但替换了时钟和参数读取；该次排查未测得原轮每段耗时，也未在排查阶段修改生产行为。详见[状态过期排查](../plans/M6.md#t05b-状态过期排查2026-11-18)。

**实际修复与复验**：用户确认后，WorldState 显式保留逐报文接收时间，按新鲜度等级匹配阈值，Safety 两次审查使用同一规则。固定两点真实 SITL 完整通过；本轮有着陆消息超过旧上限而其余报文有效的批准证据，并通过临时错误验证位置过期和末次复核漏检均会被测试发现。未整体放宽所有状态，也不能据此声称调度延迟已消除。规则及结果见[分级实施记录](../plans/M6.md#t05b-分级新鲜度实施与两点复验2026-11-18)。

**可能追问**：为什么不直接重试？把状态阈值调大是否就解决了？

**回答重点**：必须先确认旧请求是否已派发以及状态为什么过期。自动重试涉及重复动作风险；放宽阈值则改变了允许使用多旧状态的安全取舍，两者都需要额外设计与验证。

依据：[M5 4b-1](../plans/M5.md#4b-1-实施记录)、[状态聚合实现](../src/flight_agent/components/vehicle/state/world_state_aggregator.py)、[M6 T05b 失败记录](../plans/M6.md#t05b-两点飞行视觉闭环2026-11-18)。

## Q03：动作报告结束后，为什么“新观察”仍可能不准确？

**场景与现象**：M5 4b-2 中，Land 执行结束状态为已落地、未解锁；随后 Agent 观察却是已落地、仍解锁。

**定位与原因**：观察节点与执行节点各自创建状态适配器，独立接收异步更新。一次新的服务响应，不保证两个节点的快照已经同步到同一终态。

**实际处理**：保留两份原始状态，在完成记录中明确差异，不用“重新观察过了”代替终态证据。本问题尚未修复。

**验证与边界**：T05a 还出现落地上锁后聚合状态仍显示 `OFFBOARD`，该现象根因尚未定位，不能直接认定与前述差异同因。单点功能验收另外核对了 RTL 过程、落地上锁和位置；没有据此宣称末次模式显示准确。

**可能追问**：服务调用时间更晚，为什么数据还能更旧？最终应该信哪份状态？

**回答重点**：区分请求时间、消息接收时间和源采样时间。应针对待判断事实检查来源、时效和一致性；发生冲突时保留未知或不一致，不能简单选择更有利于成功的一份。

依据：[M5 4b-2](../plans/M5.md#4b-2-实施记录)、[M5 收口审查](../plans/M5.md#4c-收口审查)、[M6 T05a](../plans/M6.md#t05a-单点飞行视觉闭环2026-11-18)。

## Q04：无人机悬停了，为什么测试仍然判失败？

**场景与现象**：M4 Hold 场景有过动作执行成功、证据检查失败的运行。一轮误用综合状态年龄；另两轮 WorldState Trace 的采样间隔超过原定上限。

**定位与原因**：综合状态年龄会受低频着陆状态影响，不等于位置消息年龄。服务端 Trace 的定时记录也不能保证以足够密度记录原始位置；两轮间隔分别出现 0.885 秒和 0.731 秒。

**实际处理**：位置证据改查位置自身的新鲜标志，并补充独立客户端对真实 `VehicleLocalPosition` 的订阅。保留原有 0.5 秒间隔上限，没有通过降低判据让测试通过；生产 Gate 未变。

**验证与边界**：最终完整悬停窗口的位置采样满足间隔及误差要求。还对归档副本构造提前结束、位置偏移和缺失采样，检查均拒绝错误证据。采样仍不能证明采样间隔内的连续轨迹安全，也不等于在途安全监测已实现。

**可能追问**：命令 ACK、动作返回成功和实际稳定悬停分别证明什么？如何知道断言不是永远通过？

**回答重点**：区分命令被接受、动作完成条件满足和独立状态证据。用可控反例验证检查能发现对应错误，同时说明观察器本身也有采样限制。

依据：[M4 实际服务悬停记录及失败轮次](runtime_setup/px4_ros2_gazebo.md#m4-实际服务悬停记录)、[M4 7g-1](../plans/M4.md#7g-1-实施记录)。

## Q05：检测器单独能运行，接到 Agent 后为什么启动失败？

**场景与现象**：M6 T04c 首次运行在模型调用前失败，正式检测服务拒绝启动。

**定位与原因**：验证器把项目 uv 环境的 NumPy 放在系统 OpenCV 之前，检测进程混用了两套 Python 包环境。该轮尚未运行检测，不能归因为人物识别效果差。

**实际处理**：按既有手册让检测进程使用系统 Python，并从继承的 `PYTHONPATH` 移除项目 uv 包路径。没有临时升级、降级依赖或修改检测算法。

**验证与边界**：随后正式检测服务使用冻结的 OpenCV 环境，实际 Agent 拍照后检测通过。没有据单个进程的环境隔离声称整个项目部署环境已统一。

**可能追问**：解释器相同就一定加载同一套包吗？为什么修改其他进程的环境可能影响检测？

**回答重点**：同时检查解释器路径、模块实际加载路径和子进程继承的环境变量；遵循已验证的部署边界，再判断是否需要调整依赖方案。

依据：[M6 T04c 环境失败](../plans/M6.md#t04c-agent-拍照后检测2026-11-18)、[检测服务运行环境](runtime_setup/px4_ros2_gazebo.md#m6-t04b-图片检测服务)。

## Q06：ROS 节点都启动了，为什么首次任务没有进入模型？

**场景与现象**：M6 T03c 首次真实运行因没有初始观察，在模型调用前结束。

**定位与原因**：节点启动与有效状态就绪之间存在时间差。进程存在、服务已发布，都不能证明观察内容已经满足本轮验证前提。

**实际处理**：验证器增加有效观察等待，再运行实际有人入口；没有伪造初始状态，也没有取消生产侧的观察失败保护。

**验证与边界**：后续地面拍照及暂停失败场景通过，保留三次实际观察和两次模型回复。新增等待解决了该验证器的启动时序问题，不是通用的系统就绪协议。

**可能追问**：为什么不用固定 sleep？服务发现成功还应检查什么？

**回答重点**：等待实际需要的条件，并设置有界超时。固定延迟既可能不够，也可能浪费时间；就绪条件应随入口需要的状态而定。

依据：[M6 T03c 结果与首次失败](../plans/M6.md#t03c-agent-拍照接入2026-11-18)。

## Q07：拍照和检测都成功，为什么还要改结果交付？

**问题性质**：这是实际接入时暴露的能力缺口，不是已经发生过“返航删除照片”的故障。

**场景与原因**：早期执行器向下一动作传递紧邻前项的 `output`，对外主要返回通用摘要。该机制支持动作串联，但不足以向操作者交付整轮照片和检测结果，特别是序列尾部还执行返航时。

**实际处理**：T04d 在执行器中保留逐项原始响应，通过现有响应字段交付摘要和步骤；有人入口保存独立 JSON，并显示结果文件和图片引用。文件保存失败单独报告，避免混淆动作状态和交付状态。

**验证与边界**：先用 ROS 集成测试覆盖多组结果保留、失败停止及前轮文件不覆盖，再取得真实地面交付证据。T05a 补上实际返航落地后五项输出逐字对应的证据；此前 RTL 替身不能证明实际返航。

**可能追问**：为什么有 Trace 还需要结果文件？“动作成功”和“用户拿到结果”有什么区别？

**回答重点**：Trace 支持诊断审计，正式结果面向操作者交付。要明确每一步保存什么、怎样关联照片与检测，以及交付失败时如何如实报告。

依据：[M6 T04d](../plans/M6.md#t04d-结果交付实施2026-11-18)、[交付契约](../contracts/rosllm_services.md#m6-t04d-逐项结果交付)、[M6 T05a](../plans/M6.md#t05a-单点飞行视觉闭环2026-11-18)。

## Q08：仿真暂停后，还能不能使用最后一张图片？

**问题性质**：这是实际暂停 Gazebo 的故障注入验证，不是线上事故；它验证已有保护的效果。

**触发条件与机制**：仿真时钟停止前进，但缓存中仍可能保留图片。若只检查缓存非空，无法证明请求后取得了有效新图；若只依赖仿真时间推进来等待，暂停时也可能无法按现实时间结束等待。

**实际处理**：拍照服务结合新帧条件、源时间和本地单调时间判断有效性，并对不可用的时钟返回失败；具体时间判据以契约为准。

**验证与边界**：真实暂停并排空在途消息后，正式服务返回 `CLOCK_UNAVAILABLE`，媒体引用为空，文件数量没有增加。Agent 串联验证还确认没有后续检测调用。时间回退保护仅有构造输入验证，没有通过实际 PX4 世界回退验证。

**可能追问**：图像源时间和本地单调时间各自负责什么？缓存命中为什么不等于有效采集？

**回答重点**：源时间用于核对仿真中的帧来源与年龄，本地单调时间用于现实等待期限和接收新鲜度；不能不经转换直接比较两个时间基准的绝对值。

依据：[M6 T03b](../plans/M6.md#t03b-正式拍照服务2026-11-18)、[M6 T04c](../plans/M6.md#t04c-agent-拍照后检测2026-11-18)、[采集有效性契约](../contracts/rosllm_services.md#m6-t02b-采集有效性判据)。

## Q09：如何发现对上游代码的理解本身就是错的？

**原判断**：旧规格曾把 ROS-LLM 上游正则描述为“只捕获首个 JSON 对象”，并据此认为本项目修复了多动作提取缺口。

**核对与原因**：读取固定提交的真实源码，并用单代码块、两行 JSON 的最小输入对照。正则受结束代码围栏约束，实际上可以捕获完整多行对象，原判断不成立。

**实际处理**：更正规格，分别核对提取器和执行器解析结果。测试还发现本项目可能合并多个代码块、再由执行器拒绝；没有把 prompt 中的“唯一代码块”要求误写成提取层已经完整保证。

**验证与边界**：证据来自源码和确定性文本实验，没有运行上游 ROS 1 节点，也没有证明真实模型的格式遵循率。多代码块边界继续按暂缓范围记录。

**可能追问**：参考开源系统时，如何避免把自己的假设写成上游缺陷？为什么只测提取出的字符串还不够？

**回答重点**：冻结版本、构造最小反例、核对完整消费路径，再形成结论。发现错误解释后，应同步修正文档和对外表述。

依据：[M5 2a-1 源码对照](../plans/M5.md#2a-1-实施记录)、[当前规格的解析边界说明](../SPEC_DEV.md#12-源码证据与一一映射)。

## Q10：两点巡检都执行成功，为什么功能测试仍然失败？

**场景与现象**：M6 T05b 首轮完成起飞、两点拍照检测及 RTL，正式交付保留八项输出，两张照片与各自检测对应。但独立位置检查得到 P2 实际位移 0.4829 米，低于预设的 0.5 米下限，整轮测试失败。

**定位与原因**：P2 请求接受半径为 0.5 米，执行开始时飞机距离 P2 约 0.888 米。按请求语义，进入接受范围所需的直线位移下界约为 0.388 米；因此，该请求不保证实际移动至少 0.5 米。问题在于测试额外要求的最小位移与请求容差不协调，不能仅凭这一失败认定飞行控制错误。

**实际处理**：保留失败证据，将后续完整运行的 P2 请求接受半径及到点误差收紧至 0.25 米，保留最小位移下限 0.5 米。没有降低原位移要求，也没有用新判据把旧运行重新算作通过。

**验证与边界**：旧运行支持两点真实采集、检测对应及返航交付，但未通过全部预设验收。最初两次修改后运行被状态检查提前拒绝，不能算作位移修正有效。随后完成 Q02 的分级改动并完整复跑，P2 位移为 0.764 米、结束水平误差为 0.200 米，达到了事先固定的判据；原失败仍保留。结果见[两点复验](../plans/M6.md#t05b-分级新鲜度实施与两点复验2026-11-18)。

**可能追问**：业务代码和测试哪个错了，怎样判断？验收失败后改参数，如何避免挑选成功结果？

**回答重点**：先核对请求允许的行为和断言要求是否一致，再用实际轨迹判断。保留原失败，说明调整理由，在下一次运行前固定输入和判据并完整复验。服务返回成功、部分证据成立和整轮验收通过是不同结论。
